# Changelog

All notable changes to the Arena are recorded here. Format loosely follows Keep a Changelog.

## Unreleased

- Administering Arena is now something a person is granted, one product at a time, and the support-desk role no longer opens the Admin Panel. `staff: true` used to admit here alongside `product_admin: true`, which meant every owner and admin of the Angel support desk administered Arena — and every other first-party product — the moment they signed in, with nothing provisioned per product and nothing to revoke per product. Live, that read as "everyone has access": desk identities that had never been given Arena were reaching `/admin/` and the whole of `/api/v1/admin/*`. `product_admin: true` on the verified ID token is now the only claim that admits, still on presence of the literal `true` and still for the product the token was minted for. `staff: true` and `staff_role` are still read, and are recorded on the sign-in line and in the audit principal, but they decide nothing: a desk owner with no Arena grant now reaches exactly as much of the panel as any customer, which is none of it. The audit principal is `accounts-product-admin:<account_id>`, with the desk role appended where the administrator also works the desk; `accounts-staff:<id>[:role]` no longer exists because nothing is admitted that way. Grant Arena from the person's record in Angel Accounts (Customers → the person → Product administrator); it is read at their next sign-in. Every machine path is untouched — `ARENA_ADMIN_TOKEN`, database-issued admin tokens, `X-Admin-Token` and the loopback bypass — and remains the break-glass if Accounts is unreachable.
- The Admin Panel now says why it is shut instead of offering the same button again. Somebody signed in with Angel Accounts but holding no Arena grant used to land back on a screen whose only content was "Sign in with Angel Accounts", having just done exactly that. `GET /api/v1/admin/session` reports `signed_in` beside `authenticated`, and the panel tells that visitor the sign-in worked and the grant is what is missing. Nothing about the grant is disclosed: `signed_in` is a fact the browser holding the cookie can already read from `/api/v1/account/session`.

- The blank arena survived the engine-leak fix because disposing the failed WebGPU engine was only half of it. A canvas element keeps its rendering context for life: the first `getContext()` to succeed fixes the type, every later call for a different type returns `null`, and nothing hands the element back. `B.WebGPUEngine` asks for `'webgpu'` in its **constructor**, before `initAsync()` has had the chance to fail — so on a client whose WebGPU init fails, `#arena-canvas` is a WebGPU canvas permanently. `dispose()` frees the device and leaves the element claimed and presenting nothing, while a perfectly healthy WebGL engine renders into a context the compositor never reads. That is the blank arena with a working HUD, a live kill feed and a normal frame rate, and it is why the previous fix measurably removed the leaked engines (3 instances down to 1) without changing what anybody saw. The WebGL fallback is now handed a fresh canvas: the claimed element is replaced in place with an identical clone, which keeps its id, classes and position among its siblings (`safe-viewport.js` selects on that position). Both entry points now read the live element from the engine rather than the one they looked up before `init()`, since the old one is detached. `?webgpu=0` is unchanged and still skips the WebGPU path entirely, so it never reaches this at all.

- A client whose WebGPU init fails left the half-built engine attached to the arena canvas, where nothing could ever free it. `B.WebGPUEngine` binds to the canvas in its constructor, before `initAsync()` has had the chance to throw; the fallback then replaced the local `engine` with a WebGL one and the first was never assigned to `this.engine`, so `dispose()` could not reach it. It kept a configured `GPUCanvasContext` on that canvas for the life of the page. Measured on the live site: the default path left three Babylon engines on `#arena-canvas`, two of them WebGPU with no scenes and no render loops, against exactly one under `?webgpu=0`. On a machine where the dead context keeps presentation, the canvas shows nothing while a live engine renders into it, which is the blank arena with a working HUD and a healthy frame rate. The failed engine is now disposed before a second one is attached. `?webgpu=0` remains the triage escape hatch and is unchanged. (#228)

- The Shop quotes what the subscription costs, read from the Angel Accounts product catalog rather than held here. Arena still sells nothing and still has no price of its own: a figure written into Arena would be a second number in the world that can disagree with the card charge, which is the thing the subscription rewrite removed. The catalog publishes `price_cents`, `currency` and `interval` on its subscription block when a read has succeeded and omits them entirely when it has not, so a Shop that does not know says nothing about price rather than guessing. The read runs in the background on a fifteen-minute refresh and never on the request path, so an unreachable Accounts costs the Shop nothing; a failed read keeps the last good answer. Change the plan in Accounts and the Shop follows without a deploy.
- The subscription block said the same thing three times — a paragraph, a note beneath it, and the status line beside the button all restated what one subscription covers — which pushed the packs the page exists for below the fold. One sentence now, and it keeps the load-bearing half: nothing is sold separately.

- Fixed the Shop's Subscribe control sending people to Angel Accounts in the tab they were already using, and pointed it somewhere that exists. `ARENA_ACCOUNTS_SHOP_URL` was documented as `/shop/arena`, which is not a screen in Accounts — it answered with the "Nothing lives at that address" page, and the SPA serves that with a 200, so nothing upstream noticed. It is `/portal/apps/browse?product=arena`, which opens the catalog with Arena first. The control now opens Accounts in a new tab, because subscribing happens on another site and the packs somebody was looking at should still be there when they come back; the fallback to Arena's own Dashboard is not another site and still opens in place.
- The two sign-in screens say less. The Dashboard's explained what an API key is for, that Arena never sees a password, and what a subscription covers, before anybody had asked any of it — a wall of text with one button somewhere inside it. It is now the button and the way to get an account, with the key form still folded away for the operators who want it. The Admin Panel's lost the sentence under its button, which was also what made the button look off-centre: it set the width of the box the button was being centred in.

- The Admin Panel signs a person in through Angel Accounts and nothing else. The token form is gone, and with it the copy of an admin credential that every panel kept in `localStorage` — a token a browser can hold is a token anything reaching that origin can read, and this one opened production. Any token an older panel left in storage is cleared on sight. The machine path is deliberately untouched: `X-Admin-Token` on `/api/v1/admin/*` works exactly as before, which is how a bot, a script, or an operator at a terminal reaches the console when Accounts is the thing that is down. An Arena with no Accounts sign-in configured now says so on the login screen and names that path, rather than showing a screen with nothing to type into. The sign-in hint also names both claims that admit — the support-desk role and the per-product Arena administrator grant — because it only mentioned the desk, and somebody holding the other one had no reason to think they could get in.

- The popup watch no longer tries to tell a COOP-severed window handle from one somebody shut, which cannot be told from how quickly `closed` appears: a window closed promptly looks identical, and calling that severance left the sign-in promise hanging until its five-minute timeout — with the drawer that opens behind it never opening. Resolving false on either is fine, because every caller re-reads the session afterwards and a sign-in that did finish announces itself through the storage write.
- Fixed the popup sign-in leaving its window open on the dashboard, and the page behind it sitting signed-out for several seconds afterwards. Both were one fault: Accounts serves `Cross-Origin-Opener-Policy: same-origin`, so the moment the popup reached `/connect` the browser moved it to a new browsing context group and severed `window.opener` permanently. The landing page read the missing opener as "this was never a popup" and redirected into the dashboard instead of closing; the opener, meanwhile, saw its handle report `closed` within one 400 ms poll and concluded the sign-in had been abandoned before the person had finished typing their password. The popup now announces through the cross-tab session key, which is same-origin and crosses browsing context groups where `postMessage` cannot, and closes; it redirects only once a close has visibly failed. The opener listens for that write, and treats a `closed` reading inside the first second and a half as the severance it is rather than as somebody shutting the window. This also explains "Sign out account" intermittently answering 403: each sign-in mints a fresh CSRF token, and a dashboard never told the sign-in completed kept sending the previous session's.

- The sign-in callback now checks which issuer sent it (RFC 9207). Accounts stamps every authorization response with `iss`, and Arena verifies it against the configured issuer, refusing a response that carries somebody else's or — when the discovery document advertises the parameter — none at all. Arena talks to one provider today, so this is insurance rather than a live defence; it is the check that stops the day a second issuer is added from silently being the day a mix-up becomes possible. Kynetik already did this, and the two products should not differ on what they accept as a sign-in.
- An in-flight sign-in now survives a restart. The state, PKCE verifier and nonce were process memory, so a redeploy mid-login sent the browser back from Accounts holding a state the new process had never issued, and it was told its state was invalid with no way to tell that from a forgery — and Release Control redeploys Arena on its own. They live in `customer_login_transactions`, keyed by a SHA-256 digest of the state and holding only a digest of the browser-binding cookie, claimed with an atomic `DELETE ... RETURNING` so two callbacks racing on one state cannot both be served. A run with no database still falls back to memory, and expired rows are swept beside the sessions.
- `X-Forwarded-Proto` is believed only from a trusted proxy when deciding whether a cookie gets `Secure`. It was read from any caller, which was safe in the direction that mattered — a forged header could only turn `Secure` on — but it was inconsistent with how `ExtractClientIP` already treats the forwarded client address, and consistency about which headers are evidence is the whole point of `ARENA_TRUSTED_PROXY_CIDRS`.

- Arena is subscription-only. Every cosmetic in the catalog is included with the single monthly Arena subscription, bought and held in Angel Accounts; nothing is sold one item at a time any more. Gone with the per-item model are Arena's own Stripe checkout, order resume, subscription checkout, webhook receiver and billing portal, their routes (`/account/cosmetics/checkout`, `/account/cosmetics/orders`, `/account/cosmetics/subscription/*`, `/cosmetics/webhooks/stripe`, the admin grants, licences, memberships, access and orders endpoints, all of which now answer 404), the `ARENA_STRIPE_*` and `ARENA_COSMETICS_CHECKOUT_*` settings (ignored if still set), the `stripe-go` dependency, the Dashboard's licence assignment and purchase history, the Shop's prices and Buy controls, and the Admin Panel's Customer Access and Orders workspaces. At sign-in Arena reads the account's entitlements from Accounts and records whether the Arena product is active on `customer_accounts.subscription_active`; every paid cosmetic is unlocked or locked by that flag at read time, for every bot linked to the account, so a lapsed subscription hides the paid looks at the next read and a renewed one brings the saved loadout straight back. A locked equip answers 403 `SUBSCRIPTION_REQUIRED` with the address to subscribe at (`ARENA_ACCOUNTS_SHOP_URL`, published on the catalog), and the Dashboard and Shop say "Included with an Arena subscription" and link there. The schema change is additive: the two subscription columns are added, the licence-era tables and columns are left in place unread, and nothing is dropped.
- A product administrator for Arena, granted per product in Angel Accounts, now administers Arena alongside the support desk: `product_admin: true` on the verified ID token admits to `/api/v1/admin/*` exactly as `staff: true` does — presence of the literal `true` only, bounded by the same `ARENA_OIDC_SESSION_TTL_HOURS` grant window, re-read at the next sign-in, and never persisted. The audit principal says which grant admitted the actor (`accounts-staff:<id>[:role]` or `accounts-product-admin:<id>`), and `GET /api/v1/admin/session` reports the same `authority`. A customer cookie without either claim is still a customer.
- Added `arena-server check-oidc`, which asks Angel Accounts whether it accepts the customer OIDC client id and secret this Arena is configured with, and says which of revoked, deleted, mistyped, mis-bound or unreachable it is when it does not. It discovers the issuer, refuses a token endpoint off the issuer's origin, posts a `client_credentials` grant authenticated exactly as the code exchange is, never prints the secret, and exits non-zero on anything but an accepted credential so it can gate a deploy. Until now the only way to learn that the Arena client had been pulled on the Accounts side was to have a customer sign in and watch it fail after they had already signed in at Accounts. Pairs with the Accounts console's new Reinstate and Restore actions, which put a pulled client back without changing anything here; `.env.example` says when to run it.
- Fixed a data race on the customer session's expiry: the sliding renewal wrote `ExpiresAt` under the handler lock while cookie refresh, the session-info endpoint and `GetSession` itself read it bare, so two concurrent requests from one signed-in browser could tear the read and see a live session as expired mid-page. Every reader now goes through the lock (reproduced with `go test -race`).
- Fixed a display-name change never reaching chat: the session cache copied the name at sign-in for the full thirty-day sliding session and chat derived its handle from the copy, so a rename kept posting under the old name until the process restarted. A successful profile update now drops that account's cached sessions; the durable rows and cookies are untouched.
- Fixed the database URL being assembled by string interpolation, which made a password containing `/`, `#`, `?` or a space — most of what `openssl rand -base64` produces, and what the insecure-default warning asks for — fail to parse, burn every connection retry and stop the server with a misleading "invalid port". Credentials are URL-escaped now, and the new `ARENA_DB_SSLMODE` (default `disable`) lets a managed or remote database require TLS.
- Fixed an unsynchronised read of the database-issued admin token list in the admin middleware, which raced with a token being issued and could answer "admin token not configured" to a caller whose token was simply wrong.
- Fixed a data race between a service-status broadcast and a bot dropping mid-round: the bot's send channel was read after the engine lock was released while detach nils it under that lock. Channels are captured under the lock and the payload is marshalled once for every recipient instead of once per bot.
- The admin HTTP log and client-error reports now record the client address the way the rate limiter does, honouring `CF-Connecting-IP` and `X-Forwarded-For` only from a trusted proxy; anyone could previously pick the address the admin Errors tab attributed their abuse to.
- A customer profile's avatar colour must now be a hex colour (or empty), which every consumer already assumes when it puts the value inside a CSS `background:` declaration; the length check alone let a declaration terminator through.
- `ARENA_CHAT_HISTORY_SIZE`, `ARENA_SPATIAL_CELL_SIZE` and `ARENA_PATHFINDING_CELL_SIZE` are validated at startup: a negative history size reached `ring[over:]` and panicked on every chat post, quietly closing each poster's socket.
- Fixed the profile popup showing the wrong person when two handles were clicked in quick succession and the first request answered last.
- Retired Arena's own admin SSO application. The support-desk role in Angel Accounts is now the single source of HUMAN admin authority: an administrator signs in at Accounts like any other customer and is admitted by the platform-administrator claim on that verified sign-in (#258 added that path; this removes the alternative). Gone with it are `ARENA_OIDC_ADMIN_EMAILS` and the rest of the admin OIDC client config, the `arena_admin_session` cookie, and the `/admin/login`, `/admin/callback` and `/admin/logout` routes — those variables are ignored if still set. Two places deciding who administers the platform was one too many, and the allowlist was the one nothing revoked when somebody left the desk. The Admin Panel now bootstraps from the desk claim and sends the session's CSRF token with its mutations, so `/admin/` is reachable in a browser with no admin cookie to hold. `ARENA_OIDC_SESSION_TTL_HOURS` survives and now means only the grant window. Every machine path is deliberately untouched — `ARENA_ADMIN_TOKEN`, database-issued admin tokens, `X-Admin-Token` handling and the localhost bypass — and those are the documented break-glass if Accounts is unreachable.
- Fixed HUD and heading typography that made words run together and wrapped lines collide. `letter-spacing` is applied after every character including the space, so the negative tracking used across the site was narrowing the word gap as well as the letter fit. Measured on the live site, "Match Telemetry" rendered with a 0.153em word gap and read as a single word. Every negative tracking value now carries an equal positive `word-spacing`, which restores exactly what the tracking removed and leaves the letterforms as tight as designed; the same string now measures 0.24em. Separately, seven rules set `line-height` below 1, which makes the line box shorter than the glyphs. That is a deliberate look for a single-line display heading, but `.hud-title` wraps every round the map has a shape ("Round 77 . diamond") and `.hero h1` is capped at 11ch so it always wraps, and those wrapped lines overlapped. Leading is now at or above 1 everywhere, and `.hud-title` also gets `min-width: 0` with a non-shrinking phase chip so it stops wrapping earlier than it needs to. `scripts/test-typography-spacing.mjs` pins both rules and fails against the previous stylesheets. (#239)
- Fixed the black arena on WebGPU clients. The bloom merge pass fails to bind its textures on some WebGPU devices. It throws once, the render-loop guard contains it and drops the pass, and the arena draws. The client boots at a hardcoded 2000x2000 while the server scales the arena with bot count, so the first keyframe usually disagrees and `_rebuildForArenaSize` disposes the scene and calls `init()` again on page load, not only at a round boundary. That builds a fresh pipeline with bloom back on and re-applies the saved Bloom setting on top. The fault returns as an async `GPUValidationError` ("No bind group set at group index 1") that never throws into JS, so the containment handler is never called again. Every frame after that submits an invalid command buffer and nothing is drawn, while the loop runs at full speed and the HUD, kill feed and minimap keep updating. Containment now latches on the engine instance, which outlives the scene, arms from the GPUDevice `uncapturederror` channel as well as the synchronous throw, and is honoured by both `init()` and the settings apply. Verified on the live site in both directions, twice, at different rounds: bloom on is black, bloom off renders the full map, and enabling bloom long after startup is still black, so this is not a startup race. (#232)
- Fixed the round transition never releasing, which left the arena black with only emissive meshes drawn while the HUD, kill feed and minimap kept updating from the same payloads. The transition is entered from a `round_end`, but the only payload that reaches the release path is `arena_state`, and the server's `SpectatorState` carries no round number at all (it sends tick, round_tick, round_modifier, bots, safe_zone, pickups, kill_feed, obstacles, mask_rects, waiting_bots). The release predicate needs two finite round values, so it could never be satisfied and the map teardown that starts the transition became permanent. The release now also lifts on a `round_tick` reset, which is the signal the releasing payload actually carries, and the enter and release paths read the round number the same way. Tests pin both, with red controls. (#228)
- Fixed the blank spectator arena. Babylon zeroes `_frameHandler` before running the render callback and only re-queues the next frame after it returns, with no try/catch on that path, so a single throwing frame ends rendering permanently. Measured on a live WebGPU client: `activeRenderLoops` 1, `_frameHandler` 0, `frameId` 0, canvas black, while the spectator socket kept streaming state and a hand-called `scene.render()` still drew 166 meshes. The render callback now contains its own throws: the first failure drops the bloom pass (whose bind-group failure was the observed trigger) and keeps drawing, repeated failures drop the post-process pipeline, and the scene itself never stops. WebGPU remains the default where supported because it is a large CPU saving; `?webgpu=0` forces WebGL for triage. Also bumped the cache-bust tags on both entry points, desktop and `m/`, since the live edge serves `.js` with a four hour max-age and an unchanged `?v=` URL would not be refetched. (#228)
